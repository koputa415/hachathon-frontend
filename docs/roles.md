# T10-2 ロール別の表示

マイページで`/auth/me`が返すroleに応じて、管理者向けの権限確認ボタンだけを表示する。
一般ユーザーの出品・購入・いいねの導線は維持する。管理画面は作らない。
画面の表示制御は利便性のためであり、実際の許可はバックエンドの`AdminUser`依存で判定する。

- 新規・既存の一般ユーザーは`user`。管理者だけ`admin`。
- ロールはブラウザ保存データやJWTのクレームから読まず、サーバーのプロフィールを使用する。
- 移行前APIでroleが省略された場合は一般として扱い、未知の値では管理者表示をしない。
- 管理者用の確認はボタンを押したときだけAPIへ接続する。403では成功表示せず、確認ボタンを隠す。
- 403では一般ユーザーのログインを破棄しない。401では既存のログイン期限切れ処理を使う。

## 反映順序

1. バックエンドの`scripts.migrate_user_roles`で既存DBへrole列を追加する。
2. バックエンドのT10-1を反映し、一般で403・運用CLIで指定した管理者で200を確認する。
3. フロントのT10-2を反映する。ロール変更後の画面は再読み込みしてプロフィールを再取得する。

管理者の指定と降格はバックエンドの`cd/docs/roles.md`を参照。
公開の登録・プロフィール更新APIからロールを変更する方法は作っていない。
本番のDB・ロールは変更していない。

## ブラウザ検証

使い捨てのローカルAPI/DBを用意し、検証用ユーザーを運用CLIで管理者に設定する。
そのユーザーの検証用メールとパスワードを`ROLES_E2E_ADMIN_EMAIL`、`ROLES_E2E_ADMIN_PASSWORD`へ渡す。
本番のログイン情報をテストへ渡さない。

```sh
ROLES_E2E_BASE_URL=http://localhost:5182 ROLES_E2E_ALLOW_WRITES=1 npm run test:roles
```

一般・管理者の表示、一般からの直接API403、ブラウザ保存データや表示用プロフィールの偽装、
再読み込み、通信失敗からの再試行、未知ロールの扱いを確認する。
本番環境へ自動でテスト用ユーザーを作成しない。

検証結果：ロールのブラウザ6ケース、既存認証14ケース、CDN単体7件、lint・本番ビルドが成功。画面の管理者は使い捨てDBにのみ作成した。
